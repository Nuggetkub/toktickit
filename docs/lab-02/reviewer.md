## Notes

- Two review directions are recorded deliberately. Part 1 asks for "comments given and
  received", and a record that shows only one direction is incomplete regardless of how
  much detail it carries.
- Reviews are recorded when they happen rather than reconstructed at release. A row written
  three weeks later tends to describe what was intended rather than what occurred — a
  failure this project has already seen once, in the Lab 1 review record, where a row still
  read "review in progress" after the pull request had merged.
- **Every substantive finding in the second table came from executing his branch or checking
  it against the filesystem**, never from reading the diff alone: six concurrent uploads defeating a five-attachment limit, an executable
  accepted because the declared `Content-Type` was trusted, six requests for one search term,
  `totalPages: 0` on an empty result, a `413` answered with an HTML stack trace, and a
  `Passed` row citing a file that did not exist. Reading tells you what someone intended;
  running tells you what they built.
- **Two of my own near-misses are recorded rather than removed** — the PR #27 responsive
  assertion I went looking for and did not find, and the PR #33 conclusion I had to correct
  after checking whether the style test was in the branch's tree. A review record that only
  contains the times the reviewer was right is not a record of reviewing.
